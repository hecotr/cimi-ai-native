# CimiLoop M3 实施架构 v0.1

> 状态：实施基线
>
> 日期：2026-09-20
>
> 范围：在已冻结 M2 上交付 Claim、Evidence、Requirement Set、Independent Evaluation、精确失效传播与 Repair Loop，使 Artifact 的可交付性由证据证明。本文不实现 Test/Production Deployment、Recovery Playbook、Knowledge Closure 关闭或 Portable Export/Import。

> 实施进度：M3 Task 1–10 已完成。Artifact/Run 成功不能直接 ALLOW、未解决 Refutes 阻止 ALLOW、Evaluator 无生产写权限、旧失败与旧 Artifact 永久保留，均有自动化测试。全量验收已在 Node.js 24.15.0 + pnpm 12.4.2 基线上通过。

## 1. M3 已实现

- Protocol：Claim、Evidence、ExternalReference、GateRequirementSet、ClaimAssessment、IndependentEvaluation、EvidencePackageManifest、ImpactAssessment、RepairWorkItemLink；GateEvaluation 增加 requirement/artifact/evaluation 可选绑定；
- Store v4：上述事实只 insert；Evidence 主体绑定唯一索引；validity 由追加 ImpactAssessment + 查询投影，不改历史 payload；M0–M2 → v4 无损升级；
- Requirement Set：由 core + profile + risk + policy + contract 解析；相同输入复用 digest；未知 extension 不参与规则；
- Evidence 摄入：RecordEvidence 校验 Claim/digest/subject；仅 junit|tap|cimiloop_test_v1 可 Promote；解析失败为 Inconclusive + Impact Invalid，不猜通过；Executor 自检不能替代 independent producer；
- Evaluator：独立 package 规划 evaluation Work Item（无 workspace.write）；Context 不含 executor transcript；写入生产代码返回 `EVALUATOR_WRITE_DENIED`；evaluation retry 新建 Run；
- Gate：required 全 Satisfied 才可能 ALLOW；Insufficient → NEED_MORE_EVIDENCE；Human judgment / Conflicted → REQUIRE_HUMAN；hard policy/risk Refuted → DENY；未解决 Valid Refutes 阻止 ALLOW；相同输入 digest 复用 Evaluation，变化创建新记录；CompleteEvaluation 由 Kernel 计算结论，忽略 Evaluator 自评，不迁移 Change 生命周期；
- Impact：仅绑定变化主体的 Evidence 受影响；digest 变化 → Stale 或 Superseded；完整性/主体错配/来源不可验证 → Invalid；
- Repair：Refutes 可创建 Repair Work Item 与不可变 RepairWorkItemLink；Change 保持/回到 Executing；开放 repair 占用 Task；新 Artifact 必须重新评价，旧失败与旧 Artifact 保留；
- CLI：`claim submit/show`、`evidence record/show/package`、`evaluate request/complete/show`、`repair create`、`impact assess`；
- Workbench Change Room：Claims 覆盖/Refutes/freshness、Evaluation reason、Repair lineage。

## 2. M3 明确未实现

以下能力属于 M4 及之后，不得视为已交付：

- Test/Production Deployment、同一 Artifact Digest 的跨环境晋升流水线；
- Recovery Playbook、Reconciliation 对外部未知结果的完整运维闭环；
- Knowledge Closure 作为 Change 关闭条件；
- Portable Export/Import、Runtime ownership 转移；
- 将 Evaluator 接到真实独立 Agent Runtime（当前为确定性 Kernel 评价 + 权限隔离）；
- 完整 SPA、通用 Policy 编辑器、登录、实时协作。

## 3. 依赖方向

```text
protocol ← store ← kernel ← evaluator / orchestrator / cli / workbench
     ↑         ↑              ↑
     └─────────┴─ store-sqlite
                  context / workspace-git / runtime / runtime-claude-code
```

Kernel 是 Change 状态迁移、Gate 结论和授权判断的唯一权威。Evaluator、CLI、Workbench 和 Orchestrator 不得直写权威状态；Human Decision 不能改写 Evidence 或直接改变 Change 状态。

## 4. 关键不变量

1. Runtime 成功、Artifact 存在或模型自评不能直接 ALLOW。
2. 未解决的 Valid Refutes 必须阻止 ALLOW；冲突不做多数表决。
3. Evidence / Evaluation / Impact / Repair Link 只追加，不得原地覆盖。
4. validity 是投影，不是 Evidence payload 字段。
5. Evaluator 不得获得 `workspace.write` / `git.commit`；尝试写入记录 `EVALUATOR_WRITE_DENIED`。
6. Evaluator Context 不得包含 Executor 完整对话或临时推理。
7. 评价 retry 创建新 Run；输入变化创建新 IndependentEvaluation。
8. Repair 产生新 Artifact 后必须重新评价，不得复用旧 ALLOW。
9. 大型日志/测试输出只保存引用与 digest。
10. Secret 不得进入 Protocol、Event、Evidence Package、CLI JSON、Workbench HTML 或测试快照。

## 8. 已知限制

- Independent Evaluation 的 Gate 结论保存在 `IndependentEvaluation`，未写入 `GateEvaluation.gate_type`（该字段仍仅为 `intent|plan`）；这避免在 M3 扩大 Decision Request 类型。
- Evidence Package 是查询时投影，默认不写入 `evidence_package_manifests` 表。
- `SubmitClaim` 在已有 Contract/Policy/Risk 且尚无 Requirement Set 时由 Kernel 物化第一版 Requirement Set；没有单独的 CreateRequirementSet Command。
- Evaluator 未接入独立外部 Runtime；Orchestrator 对 evaluation Work Item 拒绝 write capability，确定性评价由 Kernel `CompleteEvaluation` 执行。
- CLI `evaluate complete` 的 `--result/--reason` 仅为协议字段，Kernel 重新计算并覆盖。
- Demo 使用 ASCII 文案，避免 Windows PowerShell 5 解析 UTF-8 无 BOM 脚本时断弦。
- Windows 上 CLI 多进程冷启动较慢；M3 CLI 场景测试超时为 90s，断言未降低。
